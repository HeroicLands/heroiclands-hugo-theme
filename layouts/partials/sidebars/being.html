{{- /* Being info sidebar — profile-card style. Layout: 1. Portrait (images/being/{shortcode}-portrait.webp on the site's asset host) 2. "Profile" header 3. Profile header dl (name / corpus / gender / born / occupation / class / realm / region / affiliations) 4. Appearance one-line composed sentence built from age, height, weight, frame, eye/hair/skin colors 5. Attributes auto-fit grid of label+value pairs 6. Skills one paragraph per category, small-caps inline list Display-name and category mappings live in data/sohl.yaml. This was two partials, `character.html` and `creature.html`, chosen by the page's content type. That type was retired — both spellings always compiled to one `being` — so the choice had to go somewhere, and the honest answer is nowhere: **every section is driven by the data it renders.** A being with no `social` block simply has no Occupation row, which is what the creature partial did by having no such row at all. Two differences between the old pair had to be settled rather than merged: - The heading was "Character Profile" or "Creature Profile". Neither is derivable now, and guessing from the optional blocks would mislabel a creature that carries `data.weight` — which the schema allows and the retirement rationale explicitly called sensible. So: "Profile". The page title and breadcrumb already name the subject. - The attribute grid differed: the character version rendered all fourteen in canonical order with an em-dash for anything missing; the creature version rendered only the ones present, because "creature stat blocks are typically sparser". The sparse rule is kept, and it costs nothing — every published `character` note carries a complete set, so "only those present" and "all fourteen" render the same markup for all of them. The em-dash was only ever distinguishable on data that does not exist, and where it would appear it asserts "this being has no Strength" when the truth is that nobody wrote one down. Reads are guarded against an absent `sohl` / `data` / `social` block throughout: the character partial could assume them, and this one cannot. **The description comes from `data:`, not from a top-level `traits:` block** (#55). `data:` is the content format's closed container for a note's own type-specific facts, and `being` declares every field this sidebar reads: `gender`, `age`, `birthday`, `height`, `weight`, `frame` and `appearance.*`. The block this partial used to read was authored at top level, where the format passes unrecognised keys straight through to Hugo — so a misspelling in it arrived here as a theme parameter rather than as a finding. Three of the reads changed shape as well as place. The old block nested its measurements — `height: {m:}`, `weight: {kg:}`, `build: {frame:}` — while the format declares `height` and `weight` as bare numbers, in metres and kilograms, and `frame` as a property in its own right. The unit conversions below are unchanged; only the path they read is. **`traits:` is still read, underneath `data:`, and normalised to that one shape.** Not for tolerance's sake: 2,533 notes across three repositories carry the old block today, each repository converts on its own schedule, and each pins this theme on a caret range inside `0.x` — so a release that read only `data:` could be adopted by a tree that has not converted yet, and every Profile row and the whole Appearance sentence would vanish from its pages in silence, `with` on an absent param rendering nothing exactly as it correctly does for a creature that has no description at all. Reading both makes the order the four changes land in stop mattering. `data:` wins wherever a note writes both, so a converted tree is never read through the old shape. The fallback is transitional and is removed once no tree writes `traits:` — tracked as the follow-up to #55. */ -}} {{- $sohl := hugo.Data.sohl -}} {{- $attrNames := $sohl.attributes -}} {{- $attrCols := $sohl.attribute_columns -}} {{- $skillNames := $sohl.skills -}} {{- $categories := $sohl.skill_categories -}} {{- /* Defaulted to empty maps, not read straight through: a being with no `sohl` or `data` block is ordinary — most creatures have neither — and `index` on a nil map is a build error, not an empty section. */ -}} {{- $attrs := dict -}}{{- with .Params.sohl }}{{- with .attributes }}{{ $attrs = . }}{{ end }}{{ end -}} {{- $skills := dict -}}{{- with .Params.sohl }}{{- with .skills }}{{ $skills = . }}{{ end }}{{ end -}} {{- /* The description, flattened to one shape from the two a tree may author. `data:` is what the format declares and it wins; the legacy top-level `traits:` block is read underneath it, normalised, so a tree that has not been converted yet renders exactly as it does today.
