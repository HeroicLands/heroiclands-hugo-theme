{{- /* Being info sidebar — profile-card style. Layout: 1. Portrait (images/being/{shortcode}-portrait.webp on the site's asset host) 2. "Profile" header 3. Profile header dl (name / corpus / gender / born / occupation / class / realm / region / affiliations) 4. Appearance one-line composed sentence built from age, height, weight, frame, eye/hair/skin colors 5. Attributes auto-fit grid of label+value pairs 6. Skills one paragraph per category, small-caps inline list Display-name and category mappings live in data/sohl.yaml. This was two partials, `character.html` and `creature.html`, chosen by the page's content type. That type was retired — both spellings always compiled to one `being` — so the choice had to go somewhere, and the honest answer is nowhere: **every section is driven by the data it renders.** A being with no `social` block simply has no Occupation row, which is what the creature partial did by having no such row at all. Two differences between the old pair had to be settled rather than merged: - The heading was "Character Profile" or "Creature Profile". Neither is derivable now, and guessing from the optional blocks would mislabel a creature that carries `traits.weight` — which the schema allows and the retirement rationale explicitly called sensible. So: "Profile". The page title and breadcrumb already name the subject. - The attribute grid differed: the character version rendered all fourteen in canonical order with an em-dash for anything missing; the creature version rendered only the ones present, because "creature stat blocks are typically sparser". The sparse rule is kept, and it costs nothing — every published `character` note carries a complete set, so "only those present" and "all fourteen" render the same markup for all of them. The em-dash was only ever distinguishable on data that does not exist, and where it would appear it asserts "this being has no Strength" when the truth is that nobody wrote one down. Reads are guarded against an absent `sohl` / `traits` / `social` block throughout: the character partial could assume them, and this one cannot. */ -}} {{- $sohl := hugo.Data.sohl -}} {{- $attrNames := $sohl.attributes -}} {{- $attrCols := $sohl.attribute_columns -}} {{- $skillNames := $sohl.skills -}} {{- $categories := $sohl.skill_categories -}} {{- /* Defaulted to empty maps, not read straight through: a being with no `sohl` or `traits` block is ordinary — most creatures have neither — and `index` on a nil map is a build error, not an empty section. */ -}} {{- $attrs := dict -}}{{- with .Params.sohl }}{{- with .attributes }}{{ $attrs = . }}{{ end }}{{ end -}} {{- $skills := dict -}}{{- with .Params.sohl }}{{- with .skills }}{{ $skills = . }}{{ end }}{{ end -}} {{- $traits := dict -}}{{- with .Params.traits }}{{ $traits = . }}{{ end -}} {{- $social := dict -}}{{- with .Params.social }}{{ $social = . }}{{ end -}} {{- $corpus := "" -}}{{- with .Params.sohl }}{{- with .corpus }}{{ $corpus = . }}{{ end }}{{ end -}} {{- $birthsign := "" -}}{{- with .Params.sohl }}{{ $birthsign = .birthsign }}{{ end -}}
